# Objective channel is a tracked file, not a prompt/CLI parameter

## Status

Accepted

## Context

On a fresh run, the supervisor injects no objective into the planner
at all: `_build_planner_prompt` (`supervisor.py:1528`) sends the
single line `"Determine the next unit of work."`, and the supervisor
itself reads no project files. Every scope decision the loop ever
makes derives entirely from what the four agent prompts under
`.opencode/agents/` tell the corresponding OpenCode agent to read.
Before this change, that was exactly two paths: `README.md` and
`docs/decisions/`.

This has no field to carry a project's actual objective. `RunState`
and `RunOptions` have no `objective`/`goal`/`spec`/`brief` field, and
no CLI flag exists to set one. `AGENTS.md` cannot fill this role: it
is gitignored (`.gitignore:1`), never copied by `init` (which is a
Git-tracked-files-only bootstrap, per ADR 0007), and referenced by
zero code and zero agent prompts. Its actual content in this repo is
host-tooling instructions (RTK, Falda), not project description, so
even if it were wired up it would be the wrong artifact to repurpose.

Two shapes were considered for the objective channel:

1. **A dedicated tracked file** (`docs/OBJECTIVE.md`), named
   explicitly in all four agent prompts alongside `README.md` and
   `docs/decisions/`. A standalone OpenCode session (or a human) edits
   this file and commits it like any other project file.
2. **A supervisor-injected prompt parameter** — a `--objective` CLI
   flag threaded into `RunState`/`RunOptions` and injected directly
   into the planner's prompt on every invocation, independent of what
   any agent chooses to read.

Option 2 is the structurally stronger design: it cannot be silently
stale (the supervisor, not the agent, decides what "the objective" is
on every single invocation) and it does not depend on every agent
prompt remembering to read one more file. It is deliberately not
chosen here because `RunState`'s on-disk schema is already scheduled
for a squash migration (backlog item 30), which several other pending
items are blocked behind (item 27's persisted denial counts, item
32's builder signal). Adding another ad hoc field to the current
schema ahead of that migration would create one more thing the
migration has to carry forward, for a feature that is easy to
retrofit once item 30 lands.

## Decision

The objective channel is `docs/OBJECTIVE.md`, a plain Git-tracked
file with no special parsing or schema. It is named explicitly, by
that path, in all four agent prompts (`loop-planner.md`,
`loop-architect.md`, `loop-builder.md`, `loop-auditor.md`) as the
first thing to read, ahead of `README.md` and `docs/decisions/`.
`docs/plans/` is also added to the planner and architect prompts in
the same change, closing a pre-existing gap where this repository's
own actively-used working-plan documents were invisible to the loop
despite being tracked.

A project (including this one) is expected to write or update
`docs/OBJECTIVE.md` from a standalone, interactive OpenCode session
before or during a `loop-supervisor run`, exactly as it would update
`README.md` or add an ADR — see the "Handing off from a standalone
session" section of `README.md`.

Redirecting an in-progress loop is done by committing a new
`docs/OBJECTIVE.md` on the integration branch; the planner reads it
fresh on every invocation, so no supervisor restart is required.

## Consequences

- No schema, CLI flag, or `RunState` change was needed; this ships
  ahead of and independent of backlog item 30.
- The objective can only be as reliable as "every agent prompt reads
  this file" — a future agent role that omits `docs/OBJECTIVE.md` from
  its own prompt would silently regress to no-objective behavior. This
  is the same class of risk `README.md`/`docs/decisions/` already
  carried before this change; it is not new, only widened by one file.
- The objective is not visible to the supervisor itself, only to the
  OpenCode agents. The supervisor cannot log, validate, or make
  decisions based on "the current objective" — for example, it cannot
  refuse to start a run with a missing or empty `docs/OBJECTIVE.md`,
  because it never reads the file.
- If backlog item 30's schema squash lands, a `--objective` /
  `RunState.options.objective` channel (option 2 above) becomes
  straightforward to add as a stronger, supervisor-owned alternative
  or complement — the supervisor could then inject the objective
  directly into every prompt rather than relying on the agent to read
  a file, and could validate it non-empty before starting a run. That
  revisit is not scheduled by this ADR; it is only noted as the
  natural next step.
- This is deliberately independent of, and a prerequisite for,
  `feature/bootstrap-skeleton`'s installable-dependency bootstrap: a
  new project generated by that work will get a stub
  `docs/OBJECTIVE.md` as part of its skeleton.
