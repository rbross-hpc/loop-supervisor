# Verification logs live under git-common-dir, and every command always runs

## Status

Accepted. Supersedes the "where full command output lives" and
"no stop-on-first-failure" paragraphs of [ADR
0026](0026-supervisor-run-verification-is-a-finding-not-a-fault.md);
everything else in ADR 0026 (the `verifying` phase, the fault/finding
policy, the prompt changes, `RunState.verification_result`'s shape and
clearing points) is unaffected and remains as decided there.

Its own "Verification logs move to ... `<run_id>/`" paragraph and the
`0o700`-parity claim are in turn superseded by [ADR
0028](0028-verification-log-directory-is-keyed-by-commit-not-run-id-alone.md):
the log directory is keyed by commit as well as `run_id`, and log
files are individually `chmod`'d to `0o600`. Everything else here
(moving out of the task worktree, why that is safe, the read-access
analysis) is unaffected. Kept for historical context.

## Context

A post-merge audit of the `feature/supervisor-verification` branch
found two real defects, both stemming from the same wrong assumption
in ADR 0026:

1. **The implementation did not match the documented policy.**
   ADR 0026 states verification "always continues to every configured
   command (no stop-on-first-failure ... a lint failure should not
   hide a downstream test failure the auditor also needs to see)."
   `_do_verifying` called the exact same `run_commands` provisioning
   uses, which stops at the first failing command. No existing test
   caught this because every verification test configured only a
   single command.
2. **Verification logs could wedge worktree cleanup.** ADR 0026 placed
   the log directory at `<worktree>/.loop-supervisor/verification/`
   and justified it as gitignored "per `_skeleton/.gitignore`." That
   file is only present in projects generated by `init` -- it is not
   present, and was never guaranteed to be present, in a project
   *adopted* via `_skills/adopt-loop-supervisor`, which is the other
   supported onboarding path (ADR 0025's `[verify]` table is written
   for exactly that case too). In a repository whose `.gitignore` does
   not reserve `.loop-supervisor/`, the log files show up as untracked
   changes: `is_clean()` returns `False`, and
   `remove_task_worktree_only` raises `GitError: refusing to remove
   worktree ... it has uncommitted changes` -- after a successful
   merge, when the task should be cleanly closeable. The same
   untracked entries also perturb `status_snapshot()`, which
   `task_status_snapshot` depends on for resume-cleanliness checks.

Both defects trace back to treating the task worktree as a safe place
to stash supervisor-internal state. `state.py` already establishes the
correct pattern for this: `save_state`/`state_dir` write under
`git_common_dir / "loop-supervisor" / "runs"`, a location that is
never inside any worktree's working tree and therefore can never
appear in that worktree's `git status`, regardless of what any
project's `.gitignore` does or doesn't contain. Verification logs
belong in the same family of location, not the worktree.

## Decision

**Stop-on-failure is now a parameter, not a fixed behavior.**
`commands.run_commands` gained `stop_on_failure: bool = True`.
Provisioning calls it with the default (a half-provisioned environment
should not continue running setup steps against it). `_do_verifying`
passes `stop_on_failure=False`, so it now actually does what ADR 0026
always said it did: every configured command runs regardless of
earlier failures, and every result is recorded.

**Verification logs move to `<git_common_dir>/loop-supervisor/
verification/<run_id>/`**, mirroring `state_dir()`'s layout exactly
one directory over. `_verification_log_dir(git_common_dir, run_id)`
builds this path, reusing `state.py`'s `validate_run_id` so a crafted
or corrupted run ID can never be used to construct a path that escapes
this directory -- the same guard `state_path()` already applies for
run state files. `_summarize_verification` takes this directory
instead of the worktree path, and `output_path` in both
`RunState.verification_result` and the auditor prompt is now an
absolute path rather than one relative to the worktree root, since the
log directory is no longer inside any worktree to be relative to.

This directory is created with `mode=0o700`, matching the restrictive
posture `save_state` already applies to run state files (`0o600`) --
verification logs can contain arbitrary build/test output, which may
include incidental sensitive detail the `_redact_secrets`/
`_truncate_message` best-effort scrubbing applied to the inline
*summary* does not extend to (the full log is written unredacted, as
before this ADR, since it is meant to be an exact record of what ran).

**Read access.** The auditor is invoked with `external_directory`
permission scoped to the task worktree's *parent* directory
(`_skeleton/opencode.json.tmpl`'s `__LOOP_SUPERVISOR_PROJECT_ROOT__`,
set from `destination.parent` in `cli.py`). The repository's `.git`
directory -- and therefore `git_common_dir` for a non-bare, non-
worktree-of-a-worktree layout -- sits directly under that same parent,
so this move requires no permission change: the auditor already has
read access to the new log location, and each `output_path` in the
prompt is a fully-resolved absolute path, so no relative-path
resolution or globbing is needed for the auditor to open one.

## Consequences

- Both audit-found defects are fixed and each has a regression test:
  a multi-command verification tuple with an early failure asserts
  every command still ran and every result is recorded, and a
  worktree-cleanliness test asserts `cleanup_worktree` succeeds after
  a verification run in a repository whose `.gitignore` does not
  contain `.loop-supervisor/`.
- Verification logs now outlive `cleanup_worktree` and the task
  worktree itself -- they are retained under git-common-dir with no
  pruning, the same way run-state JSON files already are. This is
  arguably an improvement (post-hoc diagnosis after a worktree is
  gone), but it is new unbounded retained state; tracked as backlog
  item 47, parallel to item 43's opt-in `opencode.db` pruning
  discussion, rather than addressed by coupling log deletion to
  worktree cleanup in this change.
- ADR 0026 remains accurate as a historical record of the `verifying`
  phase's design and the fault/finding policy; only its output-location
  and stop-on-failure paragraphs are superseded by this ADR.
