# Observing a detached run

Once a run is started detached (see `SKILL.md`), you have no live
console output beyond whatever `> /tmp/run.log 2>&1` captured — check
that first, then the persisted run state for anything more specific.

## The run-state file

Each run persists a JSON document at:

```
<git-common-dir>/loop-supervisor/runs/<run_id>.json
```

`<git-common-dir>` is the integration checkout's shared Git metadata
directory (`git rev-parse --git-common-dir`), not a path inside the
tracked worktree. If you don't have the `run_id` yet, it's the only
`*.json` file under that directory right after a fresh `run` starts,
or the one whose `updated_at` field is most recent.

Useful fields to inspect (read-only — do not edit this file by hand;
see `recovering-an-interrupted-run.md` for why):

- `phase` — the current phase name (`planning`, `building`,
  `auditing`, `awaiting_input`, `done`, `failed`,
  `operational_failure`, etc.).
- `original_task_id` / `task_worktree_path` / `task_branch` — which
  task is active and where its worktree lives, if one is active.
- `revision_count` / `replan_count` / `architect_retry_count` /
  `builder_guidance_count` — how close the current task is to its
  respective bounded-loop limits.
- `pending_question` — present only in `awaiting_input`; its `kind`
  and `message` tell you exactly what input the run is blocked on.
- `last_error` — present in `operational_failure`/`failed`; its
  `message`, `retryable`, and `retry_phase` fields explain what went
  wrong and whether `resume` alone will retry it.

A quick one-liner:

```bash
python3 -c "
import json
d = json.load(open('<path-to-run-id>.json'))
print('phase:', d['phase'])
print('task:', d['original_task_id'])
"
```

## Telling slow-but-healthy apart from stuck

- The run's log file (`/tmp/run.log` above) receiving no new lines for
  a while is normal — an agent call can legitimately take several
  minutes, and there is no built-in progress indicator mid-call.
- The task worktree's file mtimes advancing (`find <task-worktree>
  -newer <some-reference> -not -path '*/.git/*'`) is a reasonable
  signal that a builder invocation is actively writing files, not
  hung.
- The supervisor process itself still existing (`ps aux | grep
  loop-supervisor`) is the actual ground truth: if it's gone and the
  run state's `phase` is not `done`/`failed`, the process died
  mid-phase — see `recovering-an-interrupted-run.md`.
- Do not `git status`/edit inside the task worktree while a run is
  actively using it "just to look" — if the builder is mid-edit, you
  will observe (and could misinterpret) genuinely transient
  intermediate state.
